# コメント監査

コメントを二つの観点で調査し、**編集せずに**レポートを返すスキル。

1. **what コメント調査**: コードを見れば分かることの言い換えになっているコメントが存在するか
2. **why コメント圧縮調査**: 情報を落とさず短くできる冗長・反復コメントがあるか

依頼がどちらか一方だけならその観点だけ実施する。「〜が書いたコメント」のように著者スコープが付くことが多い。

## フェーズ 0: スコープ確定

依頼文からスコープを読み取る。

- **著者スコープ**(「takumin が書いた〜」): blame の著者でフィルタ
- **パス・ディレクトリスコープ**: 対象ファイルを限定
- **差分スコープ**(「このブランチで追加した〜」): `git diff <base>...HEAD` の追加行を対象にする
- 無指定なら作業ディレクトリ全体(ただし規模が大きければ主要ディレクトリを確認してから)

## フェーズ 1: 抽出(機械的)

### 原則: 「現在も存在するか」を問うなら HEAD を blame する

`git log -p` で履歴を走査してはいけない。後で消されたコメントを拾い、コード移動で同じ文言が複数コミットに現れて重複する。正しい基本手順:

```sh
# 1. 対象ファイル一覧(著者スコープの場合)
git log --author="<Author Name>" --name-only --format= | sort -u

# 2. 各ファイルを HEAD で blame し、著者の行だけ残す
git blame --line-porcelain HEAD -- "$f" | awk -v file="$f" '
  /^author /{author=substr($0,8)}
  /^\t/{
    line=substr($0,2)
    if (author=="<Author Name>") { ...コメント判定... }
  }'
```

### 抽出の落とし穴(全部踏んだ実績あり)

- **後置コメントは別パターンで拾う**: `code;  /* ... */` は行頭パターン `^\s*/\*` に一致しない。`;.*/\*` 系のパターンを併用する
- **`^\s*\*` を使わない**: C の継続行 `* text` を狙うと `*more = FALSE;` のようなポインタ間接参照を誤検出する。コメント開始行(`/*`, `//`, `#`)だけ拾えば継続行は文脈で読める
- **Ruby の `#` は文字列内・`#{}` を除外**する
- **全量をスクラッチパッドに保存**: `| head -N` で切ると後半を見落とす。ファイルに書いて `wc -l` で総量を確認してから読む
- 1000 行を超えたら全行を精読せず、フェーズ 2 の高収率フィルタで絞る

### 帰属の検証: blame ≠ 執筆

blame は「最後に触った人」を返す。コード移動やリフローで他人の文言がその人のコミットに載ることがある。有力候補は初出を確認する:

```sh
git log --format='%h %an %s' -S '<コメント文言>' -- <file> | tail -1
```

初出コミットの著者が別人なら「本人が書いた」ではなく「本人のコミット diff が運んだ」。レポートではこの二つを区別して書く(どちらも「その人のコミットに存在する」は真)。

## フェーズ 2: what コメント判定

### 高収率フィルタ

- **後置コメント**(`code;  /* ... */`)と**短い単独行コメント**(55 文字未満程度)が候補のほぼ全て
- 長い複数行ブロックが純粋な what コメントであることはまずない。読み飛ばしてよい(冗長性はフェーズ 3 の観点)
- テストファイルの一行コメントは通常「アサーションが検証する仕様の主張」であり、コードの言い換えではない。除外してよい

### 判定基準(必ず周辺コードを読んでから)

候補ごとに `grep -n -B5 -A5` で文脈を出して判定する。コメント単体で判定しない。

**黒(what コメント)**:
- 直前・直後のコードが同じことを字面で言っている(例: `else if (ch == 'u')` の直後の `/* skip u */`、`while (*src != '\n') src++;` の上の `/* skip to end of line */`)
- 関数名と引数の言い換え(例: `create_matchdata(...)` の上の `/* Create MatchData from captures */`)
- 包含関数のヘッダコメントが既に述べていることの再記述

**白(機能している)**:
- 魔法数の意味付け(`hi = 0x9f;  /* U+D800 to U+DFFF */`)
- ビット演算・トリックの意図(`ch ^ 0x20  /* the other case */`)
- 値のドメイン上の意味(`if (p == NULL) continue;  /* skip tombstones */`)
- 条件式の意味論的な読み(`if (code_len == begin)  /* no atom emitted */`)。字面が意味を言っていなければ白
- 呼び出し側との契約・不変条件の記述

**ボーダーライン**: 半分言い換え・半分情報(例: `# Return the capture names in group order` はメソッド名の言い換え + 順序保証の主張)。無理にどちらかに倒さず、そのまま報告する。

## フェーズ 3: why コメント圧縮判定

対象はコメント密度の高いファイル。行数を `wc -l` で見て濃いものから精読する。

### 探すパターン

1. **リフレイン**: 同じ論証がファイル内で繰り返されている。特徴的な言い回しを grep して数える:
   ```sh
   grep -n 'redefinable' <file>        # 出現回数 = 論証の反復回数
   ```
   3 回以上あれば、初出でフル論証 + 以降は一行参照に圧縮できる
2. **定型ボイラープレート**: 各メソッド・各節の頭に同じ形式文(「Falls back to the C-defined X…」など)。冒頭一括宣言に畳める。件数 × 行数で削減見積りを出す
3. **ヘッダの自己再約**: ファイルヘッダの後半段落が前半段落の内容を再列挙している。メソッドコメントがファイルヘッダを言い換えているのも同型
4. **ファイル横断の同一論証**: 同じ話が複数ファイルでフル展開されている。正典を一箇所(定義の隣が普通)に決めて他を短縮できるが、ファイルごとの自己完結性とのトレードオフなので**グレー扱いで明示**する

### 圧縮しない判断も成果物

以下は候補から外し、レポートに「対象外と判断した理由」として明記する:

- 相互参照(「As in `sub!`」「also as CRuby does」)で既に圧縮済みのもの
- 排他ビルド用の対になるテストファイル間の並行記述(同時にコンパイルされないので意図的)
- 段落ごとに別の情報を運んでいる複数段落コメント
- 各文が契約・理由を運んでいる長文(長い ≠ 冗長)

## 出力

レポート形式。**ファイルは編集しない**。

- what 調査: `file:line` 付きで「黒 / ボーダーライン」に分類し、各判定に一文の根拠。著者スコープなら「本人執筆 / コード移動が運んだ」も区別。確認したが白だった代表例にも触れる(調査の網羅性が伝わる)
- 圧縮調査: 候補を効果の大きい順に、出現箇所・回数・削減行数の見積り付きで。グレー(ファイル横断など)は分けて提示
- 「圧縮しないほうがよいもの」の節を必ず入れる
- 末尾に一行: 修正を実施する場合は削除なら redundant-comment-sweep、圧縮なら通常の編集で対応する旨を添えて、実施するかを委ねる
