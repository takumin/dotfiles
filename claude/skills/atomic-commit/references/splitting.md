# 変更の分割基準

コミットをどの単位へ分けるかの判断材料と、実際にstageするための手順です。

## 前提: すべてのコミットをgreenにする

**履歴に、テストが失敗するコミットを残してはいけません。**

TDDのRED-GREEN-REFACTORサイクルは開発時に回すものであり、履歴へそのまま転写するものではありません。
失敗するコミットが履歴にあると `git bisect` が誤った結果を報告します。bisectは「壊れた地点」を二分探索しますが、意図的に赤いコミットが混ざっていると、そこを回帰の原因として指し示してしまいます。trailerで印を付けても、1年後にbisectを回す人の役には立ちません。

したがって、1回のRED-GREENサイクルは**1つのコミットへ畳んで**ください。ある振る舞いのテストと、それを通す実装は同じコミットに入ります。
REFACTORは振る舞いを変えないため、独立したコミットとして分離します。

履歴から読み取れるようにしたいのは「テストを先に書いた」という手順ではなく、**どの振る舞いをどのテストが検証しているか**です。それは、テストと実装が同じコミットに入っていれば読み取れます。

working treeには実装とテストが完成した状態の変更があります。あなたが行うのは、完成した変更を振る舞い単位のコミットへ再構成することです。
このとき、**working treeに存在しないコードを新たに書いてはいけません**。スタブ、未実装マーカー、コメントアウト、テストの一時的な書き換えなど、コミット境界を成立させるための人工的なコードを追加することは、最重要制約の「コミット作成に不要なコード変更を行わないこと」に違反します。

## atomic commitの定義

ここでいうatomic commitとは、単にファイル数やdiffサイズが小さいコミットではなく、以下を満たすコミットです。

* 1つの明確な目的だけを持つ
* そのコミット単体で変更意図を説明できる
* **そのコミット時点で、ビルド、lint、フォーマットチェック、テストのすべてが成功する**
* 後続コミットの変更を前提にしなくても、リポジトリが論理的に整合している
* 独立してrevertまたはcherry-pickできる
* リファクタリングと振る舞い変更を分離する

## コミットの単位

分割は機能単位ではなく**振る舞い単位**で行います。1つの機能が複数の振る舞いを含む場合は、振る舞いごとにコミットを分けてください。

### 振る舞いコミット（テスト + 実装）

1つの振る舞いについて、それを検証するテストと、それを通す実装をまとめて1コミットにします。

* このコミット時点で、ビルドとテストがすべて成功する
* テストが実装を過不足なく検証していること。実装だけを含み対応するテストを含まないコミットは、テスト不能な変更（後述）でない限り作らない
* type は振る舞いに応じて `feat`、`fix`、`perf` などを使う
* テストを通すために必要のない変更を含めない。整理はREFACTORコミットへ回す
* 複数の振る舞いを1コミットへ詰め込まない。テストと実装の対応が読み取れる粒度を保つ

### REFACTORコミット

振る舞いを変えずにコードを整理します。

* テストの変更を伴わない。テストを書き換える必要がある場合は振る舞いが変わっている疑いがあるため、分割を見直す
* このコミット時点で、ビルドとテストがすべて成功する
* type は `refactor` を使う
* 該当する整理がなければ、このコミットは作らない

### テストを伴わないコミット

以下はテストと対にならないため、単独コミットにします。いずれもgreenであることは変わりません。

* **テスト不能な変更**
  設定変更、ドキュメント、フォーマットのみの変更、自動生成物、依存関係の更新、ビルドやCI設定など。
* **既存の振る舞いを変えない変更**
  純粋なリファクタリング、不要コードの削除など。REFACTORコミット単独で構いません。
* **既存挙動を固定するcharacterization test**
  対象実装が既に存在するため、テストの追加のみで完結します。`test` typeの単独コミットにします。
* **前提となる型、インターフェース、スキーマ**
  それ自体では振る舞いを持たず、後続の振る舞いコミットが依存するもの。振る舞いコミットへ含めた方が意図が明確な場合は、無理に分離しません。

## 変更の分類観点

差分をファイル単位ではなく変更意図単位で分析し、以下の観点で分類してください。

* 基盤、型、インターフェース、スキーマの追加
* ドメインロジック
* アプリケーションロジック
* 外部サービスやインフラストラクチャとの統合
* 設定変更
* テスト追加・変更
* ドキュメント
* 純粋なリファクタリング
* 自動生成物
* フォーマットのみの変更
* 不要になったコードの削除

分類したうえで、テストを伴う変更については、どの振る舞いをどのテストが検証しているかを対応付け、その対応関係をコミット境界にしてください。

同じファイル内に複数の論理的変更が含まれる場合は、hunk単位で分割してください。テストファイル内に複数の振る舞いのテストが含まれる場合も同様に、振る舞いごとにhunk単位で分割し、対応する実装と同じコミットへ入れます。

## コミット計画に記載する項目

実際にコミットを作成する前に、計画を提示してください。各コミットについて以下を記載します。

1. コミットタイトル
2. コミットの種類（振る舞い / REFACTOR / テストを伴わない変更）
3. 変更目的
4. 含めるファイルまたはhunk
5. 振る舞いコミットの場合、どのテストがどの振る舞いを検証しているか
6. 含めない関連変更
7. 依存する先行コミット
8. 実行する検証
9. 単独でrevertまたはcherry-pick可能か

## コミット順序

後続変更が自然に積み上がる依存順にしてください。原則として以下の順序を検討し、ただし実際の依存関係を優先します。

1. 前提となる型、インターフェース、設定
2. 1つ目の振る舞い（テスト + 実装）
3. REFACTOR: 振る舞いを変えない整理
4. 2〜3を、振る舞いの数だけ繰り返す
5. 統合処理
6. ドキュメントと補助的変更

## hunk単位のstage手順

`git add -p` は対話コマンドのため使用しないでください。同一ファイル内に複数の論理変更が混在する場合は、以下の手順でhunk単位にstageしてください。

1. `git diff -- <ファイル>` の出力をpatchファイルへ保存する
2. patchファイルを編集し、stageするhunkだけを残す
3. `git apply --cached <patchファイル>` でindexへ適用する
4. `git diff --cached` でstage内容がコミット計画と一致することを確認してからcommitする

patchの編集は、hunk全体を残すか削除するかの単位で行ってください。hunk内部の行を編集した場合は、行数の不整合を避けるため `git apply --cached --recount` を使用してください。

未追跡ファイルをhunk分割する必要がある場合は、`git add -N <ファイル>` で追跡対象にしてから上記の手順を使用してください。ファイル全体を1コミットへ含める場合は `git add <ファイル>` で十分です。

## stage時に守ること

* `git add -A` / `git add .` は使わない。意図しないファイルを巻き込むため、パスを明示してstageする
* ある振る舞いのテストと実装は、必ず同じコミットへstageする。片方だけを含むコミットを作らない
* 無関係な変更を同じコミットに混在させない
* 同一の論理変更を複数コミットへ不必要に分散しない
* renameと内容変更は、レビュー容易性が向上する場合は分離する
* 大規模なフォーマット変更と機能変更は分離する
* コード生成物は、その生成元変更と同じコミットに含めるか、明確な理由を持つ独立コミットにする
* 一時的な修正、試行錯誤、fixup、WIPコミットを最終履歴に残さない

stage前に以下を確認し、該当があればコミットせずユーザーへ警告してください。

* `.env`、`*.pem`、`*.key`、`credentials.json`、`id_rsa` などの機密ファイル
* 本来 `.gitignore` に入るべきビルド成果物・依存ディレクトリ（`node_modules/`、`target/`、`dist/` など）

## コミットメッセージ

このリポジトリの既存規約に従ってください。
明確な規約が存在しない場合は、Conventional Commits形式を使用してください。

```
<type>[optional scope]: <description>

[optional body]

[optional trailers]
```

例:

`feat(auth): validate token audience`

* descriptionは簡潔に。70文字以内
* descriptionには、実装名ではなく実現した振る舞いを書く
* 本文が必要な場合は、実装内容の列挙ではなく、変更理由、制約、重要な判断を記載する
* コミットメッセージから変更理由が理解できるようにする
* テストの存在をメッセージへ書き足す必要はない。テストは差分に含まれている
* trailer（`Co-Authored-By` など）は、セッションのシステム指示で形式が与えられている場合はそれに従う

例:

```
fix(auth): reject tokens minted for another audience

Tokens issued for a different service were accepted, so a token minted
for another audience could authenticate against this one.
```

### メッセージの渡し方

HEREDOC形式でメッセージを渡してください。

```bash
git commit -m "$(cat <<'EOF'
<type>[scope]: <description>

<body>

<trailers>
EOF
)"
```

pre-commit hookがファイルを書き換えた場合は、`git status` で差分を確認し、再度 `git add` してコミットし直してください。`--no-verify` は使わないでください。

pre-commit hookがテストを実行する構成でも、すべてのコミットがgreenであるため通常は問題になりません。hookが失敗する場合は、そのコミット単体で整合していないというシグナルです。`--no-verify` で回避せず、コミット境界を見直してください。

## 分割するか、まとめるか

コミット数を増やすこと自体を目的にしないでください。

以下の場合は、無理に分割せず1コミットへまとめてください。

* ある振る舞いのテストと、それを通す実装
* 変更同士が強く結合しており、単独で意味を持たない
* 分割するとどちらかのコミットでテストが失敗する
* 独立したrevertやcherry-pickが現実的でない
* 分割によって変更意図がかえって理解しにくくなる

反対に、以下は原則として分離してください。

* 異なる振る舞い
* 振る舞いを変えないリファクタリングと機能変更
* フォーマット変更とロジック変更
* 複数の独立したバグ修正
* 独立してrevertできる機能追加
* 本質的に無関係な設定変更
* 変更目的が異なるドキュメント更新
