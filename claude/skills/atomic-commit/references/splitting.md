# 変更の分割基準

コミットをどの単位へ分けるかの判断材料と、実際にstageするための手順です。

## 前提: TDDサイクルを履歴に残す

コミットは原則としてTDDのRED-GREEN-REFACTORサイクルを単位として分割します。
テストと実装を同一コミットへまとめず、失敗するテストを導入するコミット（RED）と、それを通す実装のコミット（GREEN）を分離してください。

working treeには実装とテストが完成した状態の変更があります。あなたが行うのは、完成した変更を後からTDDサイクルの単位へ再構成することです。
このとき、**working treeに存在しないコードを新たに書いてはいけません**。スタブ、未実装マーカー、コメントアウト、テストの一時的な書き換えなど、サイクルを成立させるための人工的なコードを追加することは、最重要制約の「コミット作成に不要なコード変更を行わないこと」に違反します。
サイクルとして分割できない変更は、後述の判断基準に従って統合し、その事実を報告してください。

## atomic commitの定義

ここでいうatomic commitとは、単にファイル数やdiffサイズが小さいコミットではなく、以下を満たすコミットです。

* 1つの明確な目的だけを持つ
* そのコミット単体で変更意図を説明できる
* REDコミットを除き、そのコミット時点でビルドとテストが成功する
* REDコミットは、そのコミットで追加したテストのみが失敗し、既存のテストはすべて成功する。ビルド、lint、フォーマットチェックはREDコミットでも成功する
* 後続コミットの変更を前提にしなくても、リポジトリが論理的に整合している
* 独立してrevertまたはcherry-pickできる。ただしRED-GREENは一組で扱う
* リファクタリングと振る舞い変更を分離する

## TDDサイクルの単位

サイクルは機能単位ではなく**振る舞い単位**で回します。1つの機能が複数の振る舞いを含む場合は、振る舞いごとにRED-GREEN-REFACTORを繰り返してください。

### REDコミット

対象の振る舞いを検証するテストのみを追加します。

* このコミット時点で、追加したテストは失敗する
* 既存のテストは失敗しない。既存テストが落ちる場合は分割を誤っている
* ビルド、lint、フォーマットチェックは成功する
* type は `test` を使う
* trailer に `Test-Status: red` を必ず付与する（bisectやCIから機械的に識別するため）

### GREENコミット

対応するREDコミットのテストを通す実装を追加します。

* 原則としてREDコミットの直後に置く。REDとGREENの間に無関係なコミットを挟まない
* このコミット時点で、ビルドとテストがすべて成功する
* type は振る舞いに応じて `feat`、`fix`、`perf` などを使う
* 通すために必要のない変更を含めない。整理はREFACTORコミットへ回す

### REFACTORコミット

振る舞いを変えずにコードを整理します。

* テストの変更を伴わない。テストを書き換える必要がある場合は振る舞いが変わっている疑いがあるため、分割を見直す
* このコミット時点で、ビルドとテストがすべて成功する
* type は `refactor` を使う
* 該当する整理がなければ、このコミットは作らない

### サイクルを作れない場合

以下に該当する場合はREDコミットを作らず、その理由を完了報告に記載してください。

* **テストがビルドまたはロードできない**
  対象実装が存在しないためテストのコンパイルやimportが失敗し、REDコミットがビルド不能になる場合。
  まず、working treeの変更に含まれる型、インターフェース、シグネチャの定義を先行コミットへ分離することでビルドが通らないかを検討してください。それで解消するならその先行コミットを作り、REDコミットを成立させます。
  実装本体がなければビルドが通らない言語や構成では、REDを作らずGREENへ統合してください。この場合もテストと実装は同一コミットに入りますが、それは技術的制約による統合であり、通常の分割方針への回帰ではありません。
* **テスト不能な変更**
  設定変更、ドキュメント、フォーマットのみの変更、自動生成物、依存関係の更新、ビルドやCI設定など。サイクルの対象外として通常どおり単独コミットにします。
* **既存の振る舞いを変えない変更**
  純粋なリファクタリング、不要コードの削除など。REDを伴わないREFACTORコミット単独で構いません。
* **既存挙動を固定するcharacterization test**
  対象実装が既に存在するためテストは最初から成功します。REDにはならないため、`test` typeの単独コミットにします。`Test-Status: red` は付けません。

## bisectへの影響

REDコミットはテストが失敗する状態で履歴に残るため、`git bisect` はそこで停止します。以下で緩和してください。

* すべてのREDコミットに `Test-Status: red` trailerを付与する
* 完了報告にREDコミットのハッシュ一覧を含める
* bisect実行時は該当コミットを `git bisect skip` の対象にできることを報告に添える

REDコミットを列挙するコマンド:

```bash
git log --format='%H %s' --grep='^Test-Status: red$' <ベースコミット>..HEAD
```

## 変更の分類観点

差分をファイル単位ではなく変更意図単位で分析し、以下の観点で分類してください。

* 基盤、型、インターフェース、スキーマの追加
* ドメインロジック
* アプリケーションロジック
* 外部サービスやインフラストラクチャとの統合
* 設定変更
* テスト追加・変更
* ドキュメント
* 純粋なリファクタリング
* 自動生成物
* フォーマットのみの変更
* 不要になったコードの削除

分類したうえで、テストを伴う変更については、どの振る舞いをどのテストが検証しているかを対応付け、RED-GREEN-REFACTORのサイクルへ再構成してください。

同じファイル内に複数の論理的変更が含まれる場合は、hunk単位で分割してください。テストファイル内に複数の振る舞いのテストが含まれる場合も同様に、サイクルごとにhunk単位で分割します。

## コミット計画に記載する項目

実際にコミットを作成する前に、計画を提示してください。各コミットについて以下を記載します。

1. コミットタイトル
2. TDDサイクル上の位置（RED / GREEN / REFACTOR / サイクル外）
3. 変更目的
4. 含めるファイルまたはhunk
5. 含めない関連変更
6. 依存する先行コミット
7. 実行する検証と、その期待結果（REDコミットでは、どのテストが失敗すれば正しいか）
8. 単独でrevertまたはcherry-pick可能か

サイクルを作れずGREENへ統合したものがあれば、その理由も計画に明記してください。

## コミット順序

後続変更が自然に積み上がる依存順にしてください。原則として以下の順序を検討し、ただし実際の依存関係を優先します。

1. 前提となる型、インターフェース、設定。対象の振る舞いのテストがビルド可能になるために必要なもの
2. RED: 1つ目の振る舞いの失敗するテスト
3. GREEN: そのテストを通す実装
4. REFACTOR: 振る舞いを変えない整理
5. 2〜4を、振る舞いの数だけ繰り返す
6. 統合処理。これもテスト可能であればRED-GREENで回す
7. ドキュメントと補助的変更

## hunk単位のstage手順

`git add -p` は対話コマンドのため使用しないでください。同一ファイル内に複数の論理変更が混在する場合は、以下の手順でhunk単位にstageしてください。

1. `git diff -- <ファイル>` の出力をpatchファイルへ保存する
2. patchファイルを編集し、stageするhunkだけを残す
3. `git apply --cached <patchファイル>` でindexへ適用する
4. `git diff --cached` でstage内容がコミット計画と一致することを確認してからcommitする

patchの編集は、hunk全体を残すか削除するかの単位で行ってください。hunk内部の行を編集した場合は、行数の不整合を避けるため `git apply --cached --recount` を使用してください。

未追跡ファイルをhunk分割する必要がある場合は、`git add -N <ファイル>` で追跡対象にしてから上記の手順を使用してください。ファイル全体を1コミットへ含める場合は `git add <ファイル>` で十分です。

## stage時に守ること

* `git add -A` / `git add .` は使わない。意図しないファイルを巻き込むため、パスを明示してstageする
* REDコミットには対象の振る舞いのテストのみを含める。実装コードを混入させない
* GREENコミットにはテストを追加しない。テストの追加はREDコミットで行う
* 無関係な変更を同じコミットに混在させない
* 同一の論理変更を複数コミットへ不必要に分散しない
* renameと内容変更は、レビュー容易性が向上する場合は分離する
* 大規模なフォーマット変更と機能変更は分離する
* コード生成物は、その生成元変更と同じコミットに含めるか、明確な理由を持つ独立コミットにする
* 一時的な修正、試行錯誤、fixup、WIPコミットを最終履歴に残さない

stage前に以下を確認し、該当があればコミットせずユーザーへ警告してください。

* `.env`、`*.pem`、`*.key`、`credentials.json`、`id_rsa` などの機密ファイル
* 本来 `.gitignore` に入るべきビルド成果物・依存ディレクトリ（`node_modules/`、`target/`、`dist/` など）

## コミットメッセージ

このリポジトリの既存規約に従ってください。
明確な規約が存在しない場合は、Conventional Commits形式を使用してください。

```
<type>[optional scope]: <description>

[optional body]

[optional trailers]
```

例:

`feat(auth): validate token audience`

* descriptionは簡潔に。70文字以内
* 本文が必要な場合は、実装内容の列挙ではなく、変更理由、制約、重要な判断を記載する
* コミットメッセージから変更理由が理解できるようにする
* trailer（`Co-Authored-By` など）は、セッションのシステム指示で形式が与えられている場合はそれに従う

### REDコミットのメッセージ

REDコミットは以下の形式にしてください。

```
test[optional scope]: add failing test for <behavior>

<なぜこの振る舞いが必要か>

Test-Status: red
```

例:

```
test(auth): add failing test for token audience

Tokens issued for another audience were accepted, so a token minted
for a different service could authenticate against this one.

Test-Status: red
```

* descriptionには、実装名ではなく検証する振る舞いを書く
* `Test-Status: red` はtrailerブロックに置く。他のtrailerと同じブロックに並べてよい
* このtrailerはREDコミットにのみ付与する。GREEN、REFACTOR、characterization testには付けない

### メッセージの渡し方

HEREDOC形式でメッセージを渡してください。

```bash
git commit -m "$(cat <<'EOF'
<type>[scope]: <description>

<body>

<trailers>
EOF
)"
```

pre-commit hookがファイルを書き換えた場合は、`git status` で差分を確認し、再度 `git add` してコミットし直してください。`--no-verify` は使わないでください。

pre-commit hookがテストを実行する構成では、REDコミットがhookによって拒否されます。この場合は `--no-verify` で回避せず、次のいずれかを選んでください。

* REDコミットを作らずGREENへ統合する
* hookの設定変更が必要であることをユーザーへ報告し、判断を仰ぐ

## 分割するか、まとめるか

コミット数を増やすこと自体を目的にしないでください。

以下の場合は、無理に分割せず1コミットへまとめてください。

* REDコミットがビルド不能になる（前掲「サイクルを作れない場合」を参照）
* 変更同士が強く結合しており、単独で意味を持たない
* 独立したrevertやcherry-pickが現実的でない
* 分割によって変更意図がかえって理解しにくくなる

反対に、以下は原則として分離してください。

* 失敗するテスト（RED）と、それを通す実装（GREEN）
* 振る舞いを変えないリファクタリングと機能変更
* フォーマット変更とロジック変更
* 複数の独立したバグ修正
* 独立してrevertできる機能追加
* 本質的に無関係な設定変更
* 変更目的が異なるドキュメント更新
